What this run is for, and what it is not
----------------------------------------

The acceptance this leaf really wants on a device — a sub-cap EPUB added from
FastReader appearing and reading on reader-web, an over-cap EPUB refused with
the policy's cap, a duplicate add making no second row, `am force-stop`
mid-transfer resuming without a duplicate, and the stage import records showing
zero imports before the consent tap — all need the owner's signed-in stage
Reader account. Nobody on this run has it. Those five are recorded as
`PENDING OWNER TEST` on the PR and in the effort's owner-test list; none of them
is claimed here.

What this run does prove is the thing nothing else could:

1. The new process-scoped wiring does not take the app down. `AccountImports`
   is constructed in `FastReaderApplication.onCreate` beside the sync engine,
   and the foreground observer gained an `onStop` for the first time. A unit
   test cannot see either.
2. Signed out, the shelf is still exactly the 1.6.0 shelf. No device book
   offers **Add to account library**, because `addToAccountFor` returns null
   for every row while `AccountSyncPhase.SIGNED_OUT` — which is REQ-505's
   "signing in or opening never adds a book" at its strongest: there is no
   control to press at all.
