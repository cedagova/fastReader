Why this run exists
-------------------
REQ-510 names it as a clause of its own: "the docs/evidence/46/ backup procedure
while a copy exists transfers zero bytes". docs/evidence/46/ proved the exclusion
on a device holding a catalog, covers and a theme mirror. Increment 003 puts a
new *kind* of file in private storage for the first time since then — a whole
book — so the question is no longer the one #46 answered. This is the same
procedure, the same two transports, on a device that is holding one.

The static half is proven without a device by AppVersionTest ("downloaded copies
live in a domain the backup rules exclude"), which derives the directory from
AccountCopyStore.DIRECTORY_NAME and asserts it sits directly under filesDir, in
the `file` domain that data_extraction_rules.xml excludes in both sections. This
run is the behavioural half.

How the copy got there
----------------------
Written directly into the app's own private storage with `run-as`, under exactly
the name and in exactly the directory AccountCopyStore places a verified copy
under:

    files/account-copies/copy-<sha256 of the file's bytes>.epub   (524,288 bytes)

and the script named it after the digest it had just computed of those bytes, so
the file is the shape the production writer produces. It was NOT downloaded
through the real grant, because that needs the signed-in stage account and the
owner is not available for this run (see the PENDING OWNER TEST list). That
makes no difference to what is being measured: Android's backup agent reads the
filesystem, and the rules exclude a *domain*, not a provenance. What is proven
here is that a file of this kind, in this directory, moves zero bytes on both
transports — which is the claim the privacy statement makes.

The two transports, and what each one proves
--------------------------------------------
  com.android.localtransport/.LocalTransport                    cloud backup
  com.google.android.gms/.backup.migrate.service.D2dTransport   device transfer

The cloud path is refused outright ("Backup is not allowed"), which is
android:allowBackup="false". The device-transfer path ignores that attribute, so
there it is the rules file that empties the payload — the same split
docs/evidence/46/ isolated with its build B control.

Result: ZERO bytes on both transports, and no FastReader path in the stored blob
on either. Identical to build C of docs/evidence/46/, on a device that is also
holding a 512 KiB account copy.

The copy was deleted again at the end of the run.
